# AEGIS audit — 2026-10-10

**Scope:** `AEGIS/apps/extension` end to end, plus the agent/model path and the harnesses. Code
read in full: the side panel, the session loop, the agent, egress, privacy builder, guard, image
attach, capture, perception client, content port, extractor, observers and dispatch. The worker and
the recognizers were sampled. Architecture reference: [architecture-as-built.md](architecture-as-built.md).

**Checks run today:** `pnpm -r typecheck` passes, `eslint .` passes, extension unit tests
**105 files / 1,070 tests pass**. None of the defects below is caught by them: the unit tests drive
`Session` with synchronous fakes, and the harnesses run the dev build.

**Confidence labels:** *Verified* = traced through the code, the failure path is certain.
*Likely* = the code path is certain but its frequency on real sites needs a run to confirm.
*Contradiction* = the code disagrees with itself and needs a measurement.

---

## Summary

The extension can work on a calm, single-site page. It fails on ordinary real sites for three
reasons that compound:

1. **Any failure becomes a stop.** Every step must carry a redacted screenshot. Five failed steps
   in a row end the task, and the screenshot path fails easily on dynamic pages (B4) or after a
   cross-origin move in release (B5). Separately, two malformed model replies end the task outright
   (B3).
2. **The model is starved of context.** It is not told which page it is on and sees 10 snippets of
   page text. It has no memory between steps beyond op codes and no reasoning budget, and it must
   answer in 120 words (Q1–Q5). That is the "quality is not up to the mark" problem: the model
   is not given enough to do better.
3. **Stop and cleanup are unreliable.** Stopping during a confirmation leaves the task alive, and a
   later click can still act on the page (B1). A content script that fails one `extract` hangs the
   task forever (B2).

## P0 — breaks tasks or safety

### B1. Stop during a confirmation card leaves the task running; "Allow" afterwards acts on the page — *Verified*
- `handleStop` resolves the grant and question cards but not the confirmation card
  ([main.tsx:716-722](../apps/extension/entrypoints/sidepanel/main.tsx#L716-L722)).
- The session awaits `confirm()` and then dispatches **without checking `isFinished()`**
  ([session.ts:1284](../apps/extension/src/host/session.ts#L1284),
  [session.ts:1318-1330](../apps/extension/src/host/session.ts#L1318-L1330)).
- `start()` never returns, so cleanup never runs
  ([main.tsx:707-713](../apps/extension/entrypoints/sidepanel/main.tsx#L707-L713)). The port and
  content observers stay alive, the worker stays loaded with ~110 MB of models, and the
  `tabs.onCreated` listener leaks.
- **Effect:** the confirmation card stays on screen after Stop. Pressing "Allow" on it clicks the
  button on the page (e.g. "Send", "Buy") for a task the user already cancelled.

### B2. A content-script failure on `extract` hangs the task forever — *Verified*
- `requestGraph()` has no timeout ([session.ts:609-615](../apps/extension/src/host/session.ts#L609-L615)).
- If `sendGraph` throws in the page, the content script answers only `dispatch-action` failures and
  sends nothing for `extract` ([content/port.ts:103-108](../apps/extension/src/content/port.ts#L103-L108)).
- On a page that does not mutate (so no auto-sent graph resolves the wait), the step never ends.
  Stop does not reject the pending graph either, so cleanup never runs (same leak as B1).
- **Effect:** the panel shows "Running" indefinitely.

### B3. Two malformed model replies end the whole task — *Verified*
- `planInvalid` is HTTP 422, non-retryable ([agent/errors.ts:42](../apps/extension/src/host/agent/errors.ts#L42)).
  `classifySendFailure` treats non-retryable errors as fatal
  ([session.ts:291-303](../apps/extension/src/host/session.ts#L291-L303)), so `serverFailure`
  calls `stop('SERVER_ERROR')`.
- The same applies to `upstream_too_large` after two prompt rebuilds.
- **Effect:** after one corrective retry, the task stops with
  `SERVER_ERROR: PLAN_INVALID (...)`. This contradicts the no-interruption decision (2026-09-29).
  It is made more likely by Q4: the model has no reasoning budget and replies in strict JSON mode.

### B4. Screenshots fail on dynamic pages, and no screenshot means no step — *Likely*
- The geometry digest covers **every** node seen
  ([run-step.ts:154, 176](../apps/extension/src/host/perception-client/run-step.ts#L154)), not
  only redaction-bearing ones as designed. "After" is all nodes after a fresh extract, so any node
  that appeared, moved or resized during the capture fails the check: a carousel, ad slot, lazy image
  or sticky header.
- The retry switches to pixel-verified mode, which is accepted only if the worker's whole-frame face
  **and** text passes both completed. After 4 attempts the step fails. After 5 failed steps the task
  stops (`RECOVERY_EXHAUSTED`).
- Each attempt costs a capture, a full DOM extract and 0.7–2.8 s of back-off, so even successful
  steps are slow on busy pages.

### B5. Release capture depends on a toolbar click that Chrome withdraws on cross-origin navigation — *Contradiction*
- In release, screenshots work only through `activeTab`
  ([background.ts:14-49](../apps/extension/entrypoints/background.ts#L14-L49)), which is lost when
  the task moves to another site. Every new site then raises "click the AEGIS icon" and the task
  waits.
- The code contradicts itself on whether the "Allow all sites" button fixes this:
  - [background.ts:22-25](../apps/extension/entrypoints/background.ts#L22-L25) says a
    runtime-granted optional `<all_urls>` does **not** satisfy `captureVisibleTab` ("re-measured in
    Chrome 144… and Chromium 153").
  - [capabilities.ts:38-42](../apps/extension/src/host/platform/capabilities.ts#L38-L42), the
    `grant-gate.ts` header and the panel's "Site access: all sites (screenshots of any tab…)" note
    say it does.
  - If background.ts is right, the card's "Allow all sites" button loops: grant → capture refused →
    card again.
- Dev builds make `<all_urls>` a **required** permission
  ([wxt.config.ts:66](../apps/extension/wxt.config.ts#L66)), so `probe_site.py --watch`, the
  eval and `run_demo.py` never exercise the release grant flow. Only `release_smoke.py` uses the
  release build, and it does not do a cross-site task.

### B6. Each step pulls the task tab to the front — *Verified*
- `captureTargetTab` activates the task tab for the capture and then restores the previous tab
  ([capture-tab.ts:85-103](../apps/extension/src/host/capture/capture-tab.ts#L85-L103)).
- **Effect:** while a task runs, the user cannot work in another tab of the same window; it flips
  back every few seconds. This follows from "every step has a screenshot", but it is a visible defect.

## P1 — response quality

### Q1. The model is not told where it is — *Verified*
- `buildUserMessage` sends no URL, origin or **title**
  ([prompt.ts:220-249](../apps/extension/src/host/agent/prompt.ts#L220-L249)). The title is
  sanitized in the builder ([builder.ts:625, 646](../apps/extension/src/host/privacy/context/builder.ts#L646))
  and then dropped. `pageCategory` is hard-coded to `'unknown'`
  ([main.tsx:657](../apps/extension/entrypoints/sidepanel/main.tsx#L657)).
- Not sending the URL is a recorded privacy decision (OQ-11, schema comment). The title is allowed
  by the schema but unused. The model chose the `navigate` / `open_tab` URLs itself, so it already
  knows them.
- **Effect:** the model re-opens sites it is already on, and cannot tell a search results page from
  a product page except by squinting at the screenshot.

### Q2. Almost no page text reaches the model — *Verified*
- The prompt caps: 45 elements with names ≤ 50 chars, **10 text runs × 120 chars, in-viewport only**
  ([prompt.ts:55-60, 225-233](../apps/extension/src/host/agent/prompt.ts#L55-L60)).
- Reading tasks ("summarise", "what's the price", "compare") must be answered from a ≤ 1280 px,
  partly grey/black WebP. The caps were sized for an 8K-TPM free-tier budget, not for answer quality.

### Q3. No working memory across steps or pages — *Verified*
- History is the last 5 entries of `op alias -> outcome`. Aliases are renumbered every step, and an
  entry keeps its alias only while that element is still listed
  ([prompt.ts:196-208](../apps/extension/src/host/agent/prompt.ts#L196-L208)).
- There is no field for the model to note what it has learned. What it read on page A is gone on
  page B. Earlier `report` texts are never fed back.
- **Effect:** multi-page tasks loop or end with a thin answer.

### Q4. No reasoning and a tight answer budget — *Verified*
- `reasoning_effort: 'none'`, `temperature 0`, `json_object`, `max_tokens 900`
  ([model-client.ts:18-29](../apps/extension/src/host/egress/model-client.ts#L18-L29)).
- The plan schema has no thought or progress field, and the system prompt caps answers at
  **120 words** ([prompt.ts:34](../apps/extension/src/host/agent/prompt.ts#L34)).
- **Effect:** short, shallow answers, frequent wrong-element choices, and invalid JSON that triggers
  B3.

### Q5. The answer is buried in a debug log — *Verified*
- The final answer is the **last** `report` only, shown at the bottom under Setup and per-step
  sections ([RunLogView.tsx:358-410](../apps/extension/src/ui/RunLogView.tsx#L358-L410)).
  Reports from earlier steps are not shown in the result. The panel is laid out for developers, not
  for someone who asked a question.

### Q6. Confirmation cards interrupt routine actions — *Verified*
- Every `click_point` is "medium" risk, so it always asks
  ([risk.ts:43](../apps/extension/src/host/actions/risk.ts#L43)).
- Any element whose name contains send/delete/remove/pay/purchase/**buy**/transfer asks too, which
  covers ordinary product cards and links on shopping sites.

### Q7. The model is offered an op that does nothing — *Verified*
- `request_observation` is listed in the system prompt but runs as a no-op
  ([dispatch.ts:60](../apps/extension/src/host/actions/dispatch.ts#L60), then falls through in
  `actOnPlan`). A step that uses it is wasted.

### Q8. The free tier caps speed — *Constraint, not a bug*
- One screenshot step is ~5.5K tokens against an 8K tokens/minute limit for the only Groq vision
  model, so at most about one step every ~40 s. A 10-step task takes ~7 min against a 10-minute
  wall-clock budget ([budgets.ts:25](../apps/extension/src/host/controller/budgets.ts#L25)).
  The Q2 caps exist to fit this budget. Better quality needs either a bigger budget (paid tier or
  another provider) or fewer image tokens.

## P3 — dead code, duplication, drift

- **Dead code:** `host/capture/service.ts` and `capture/rate-limit.ts` (no importer);
  `listenForPermissionRevocation`; budget limits `capturesPerStep`, `localRepairsPerAction`,
  `settleTimeoutMs`, `serverResponseTimeoutMs` (never enforced); controller state `BLOCK` and event
  `reconciled_locally` (never sent); `ui/ReportView.tsx`; `ContentPortHandlers.onNavigated`.
- **Two prompt implementations:** TypeScript `src/host/agent/prompt.ts` and Python
  `server/gateway/.../prompt/`. `probe_site.py` measures prompt size with the Python one, so a
  change to one silently diverges from the other.
- **Model specs copied by hand:** five specs in `main.tsx:64-115` duplicate `models.manifest.json`.
- **Comment bloat:** long dated narratives ("T-6.8, 2026-09-26: real, previously-undiscovered bug…")
  make up a large share of `main.tsx`, `session.ts` and `wxt.config.ts`. `main.tsx` mixes UI,
  wiring, tab control and model specs in one 1,083-line component.
- **Stale guidance:** `AEGIS/CLAUDE.md` points to `docs/CURRENT_BUILD.md`, `TASKS.md`,
  `HISTORY.md` and `DECISIONS.md`, which were deleted. `docs/planning/bugs/tasks.md` has every box
  unchecked, though R-5 reconnect and A8 `MODEL_STOPPED` are implemented.
- **No measurements:** the last eval report (2026-09-29, n=166) shows `—` for every official metric.
  No number in the docs is currently backed by a run.

## What is solid

- The privacy core: one guard choke point, branded payloads, an in-memory vault, protected fields
  never read, an independent tripwire before the model call, and `fetch` confined by lint.
- Navigation re-attach, following new tabs, the buffered port, and the self-healing perception
  worker all handle real edge cases.
- Model-client failure mapping to a closed vocabulary, token-bucket pacing, and the 413
  prompt-shrink path.
- Clean layering by runtime context, with typecheck and lint holding it.

## Decisions needed before planning

1. **Screenshot on every step (current rule) vs. when it is needed.** This rule is the main source
   of task stops (B4, B5, B6) and of latency (Q8). Options: keep it but make capture far more
   tolerant (digest only over redaction-bearing boxes), or allow a text step when the page is
   structurally covered. That second option reverses the 2026-09-30 decision.
2. **What page identity the model may see.** Page title only (already sanitized, schema-allowed),
   or title plus hostname (reverses OQ-11).
3. **Model budget.** Stay on the Groq free tier (accept ~40 s/step and the small context), or plan
   for a paid tier or another provider, which unlocks Q2–Q4.
4. **Release permission model.** Measure whether optional `<all_urls>` satisfies `captureVisibleTab`
   in current Chrome (resolves B5), and whether dev builds should switch to the release permission
   model so harness runs match what users get.

### 2026-10-15: multi-site tasks, memory across pages, page waits

**Reported by the user** (their own Chrome; task: "compare the price of the book across different
websites and add the book 'deep work' into my cart wherever it is most cheaply available"):
- it only went to Amazon;
- it took about 54 s;
- it sometimes added the same product to the cart twice, after coming back to a page it seemed
  not to remember.

**Causes found in code and in a baseline visible run**
- HISTORY was the last **5** steps, each recorded only as element ids (`click e12 -> acted`). Ids
  mean nothing once the page changes, so after any navigation the model could not tell it had
  already pressed "Add to Cart".
- No rule said to compare several sites, to skip a site that blocks, or to do a lasting action
  once. In the baseline run (DuckDuckGo start), Amazon blocked the test browser and the model
  stopped the whole task.
- The model did not know the user's country: it chose amazon.com.
- After every navigation the panel waited for the tab's load event **three times** (up to 2.5 s
  each), and the page-ready check waited up to **8 s** for pictures on every new page. Shops
  lazy-load pictures without end, so these caps were often spent in full.

**Fixes**

| Fix | Where |
|---|---|
| History entries carry the page title and each target's name, both as sent in that step (already sanitized and guarded); the page is printed only where it changed. (The window was first raised to 15 steps; replaced the same day by whole-task memory, see below.) | `protocol/schema/sanitized-context.schema.json` (`page`, `actions[].name`, `maxItems` 15; types regenerated), `session.ts`, `privacy/context/builder.ts`, `agent/prompt.ts` |
| One-time clicks (add to cart / basket / bag / wishlist, buy now, place order, subscribe, book now, reserve, follow, vote, RSVP) are done at most once per page title per task; a repeat is skipped and HISTORY says "NOT repeated: … already pressed on this page at s-N" | `actions/risk.ts` (`isOneTimeAction`), `session.ts` (`doneOnce`) |
| Prompt rules: compare at least 3 sites, one NOTES line per site; skip a site that blocks, asks for a login or lacks the item; never stop while other sites remain; go straight to a known (search) URL with navigate, never type a URL into a search box; lasting actions once, then "DONE: …" in NOTES, and check the result on the next step before sending done | `agent/prompt.ts` |
| `REGION: <ISO alpha-2>` line from the browser's language (`en-IN` → `IN`); it is not page data, and anything that is not two capital letters is dropped | `main.tsx` (`browserRegion`), `agent-client.ts`, `engine.ts`, `prompt.ts` |
| One tab-load wait after a navigation, not three: `runNavigation` waits only for the load to start, and re-attaching after a navigation does not wait again | `main.tsx` |
| Page-ready caps lowered from 8 s to 3 s (new page) and from 3 s to 1.5 s (later looks); a picture still loading is sent grey | `session.ts` |

### 2026-10-15: agent tools (Stage 1) and smart-model routing (Stage 2)

The product owner asked for Claude-like agentic behaviour. The JSON action contract is kept, not
replaced by native function calling: it had no rejected plans in recent runs, so the gain was
uncertain and the rewrite large. The new tools are ops in the same validated contract.

**Enforced checklist** (`agent/plan.ts` `AgentSession.checklist`, `agent/engine.ts`, `agent/prompt.ts`)
- The model writes `"checklist"` on its first step: every sub-goal, one item per site to compare,
  then each action and its check.
- Later steps send only the items that changed. Items can be added and their status changed
  (todo / done / skipped with a reason), never removed: an update that omits an item leaves it as
  it was.
- **`done` is refused** while any item is todo. The refusal names the open items and goes through
  the one corrective retry, which the smart model makes.
- The checklist lives on the device, like the notes: model-written text about sanitized input.

**Smart-model routing** (`egress/providers.ts` `smartModels`, `egress/model-client.ts`, `agent/engine.ts`
`tierFor`)
- Gemini's smart models are `gemini-3.6-flash` and `gemini-3.5-flash` (about 20 free requests a
  day each).
- The smart model makes the first step (the plan), any step after an off-course outcome (failed,
  no visible change, rejected, repeated plan, refused, blocked), and every correction. Routine
  steps go to Flash-Lite.
- A smart model that is used up (daily 429), missing (404) or overloaded (5xx) makes the step
  routine; it never stops the task.
- The run log shows which model answered and whether it was the smart one.

**Model-call resilience** (`egress/model-client.ts`)
- **5xx / "high demand":** the step goes to the next model at once, and the overloaded model is
  passed over for 60 s. Before this, a 503 from 3.6 Flash was re-sent to the same model six
  times: 42 s and 12 requests.
- **Hedging:** a reply slower than 7 s is raced against the same request to the next model with
  its own quota (Gemini). The first 2xx answer wins and the other request is aborted at once.
  Measured Google latencies in one run went up to 29 s for an ordinary step.

**New tools** (contract: `action-plan.schema.json`; payload: `sanitized-context.schema.json`
`text_scope`, `tabs`; types and Pydantic models regenerated)

| Op | What it does | Privacy |
|---|---|---|
| `find {text}` | Content script scrolls the next occurrence of `text` into view (`dispatchFind`) | Page text nodes only, never a field's value; skips hidden text and AEGIS's own UI; the host refuses text shaped like personal data (email, 6+ digit runs, placeholders), which could probe for a value the model never saw |
| `read_page` | The next scan carries the whole document's text runs (`extract` with `fullText`; graph marked `textScope: page`); the prompt allows 5× the runs and 3.5× the characters for that step | The same Channel D/T sanitization and the guard's sweep of every string leaf. The element list keeps its usual range |
| `switch_tab {tab}` / `close_tab {tab}` | TABS lists the tabs this task has used (first-use order, current marked); switching re-attaches to that tab's page; the current tab cannot be closed | Only the task's own tabs are listed. Titles are sanitized like the page title and swept by the guard |

**Speed diagnosis.** A numbers-only `observe timings {attach, ready, graph}` log line is written
when an observation takes over 2 s. On Flipkart, 7.6 s of one observation was re-attaching while
the next page loaded; the page scan itself took 0.14 s.

cases in `autonomy.spec.ts` and `model-client.spec.ts`). Gateway: 166. Lint and typecheck pass.
